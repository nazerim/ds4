**The minimal correct shape is ~30 lines, and the PR already has what it needs.** The store function
`ds4_kvstore_store_live_prefix_text` **already takes `ds4_engine *engine`** at PR head (line 930), so
the current fingerprint is computable at the reuse site with no plumbing. A port is an *extraction*:
1. lift the PR's inline load-side stamp read (`ds4_kvstore.c:1283-1318`) into a path-based helper
   returning a three-state verdict (our `ds4_kvstore_existing_stamp_verdict(path, cur_fp)` is the model);
2. call it in the reuse shortcut (`:1003-1006`: compat → `kv_cache_rewrite_trailer` → `return true`, the
   site with no stamp check) and take the normal staging/atomic-replace route on anything but MATCH.

**The trap a naive port walks straight into:** the PR's `kv_cache_existing_compatible` **`unlink`s the
file when it judges it incompatible**. A fingerprint mismatch is *not* the same kind of incompatibility
as a wrong-model file: deleting on mismatch destroys the self-healing path, because the next store rewrites
a correct checkpoint whereas an unlink costs a full cold prefill every time until one succeeds. Our fix
refuses reuse and **keeps** the file for exactly this reason, and distinguishes UNREADABLE (unverifiable)
from MISMATCH (verified stale). Any port must preserve that asymmetry or it trades a correctness bug for
an availability one.

**Also verified: the PR's load-side positioning is correct.** Its read seeks to `payload_start +
payload_bytes` where `payload_start = ftell(fp)` is taken *after* the text `fread`, i.e. it lands past
text+payload — the same place our parser lands. So this is a store-side gap only; do not "fix" the load path.

**Recommendation:** keep reply 2 as staged — it discloses the gap and offers the fix — and **do not
preemptively push a port**. Publishing an unrequested ~30-line rework of a reviewer's own PR into a

## 11. #1343 bit collision — measured on the live cache (2026-11-21), it is NOT hypothetical

Full ext_flags census over all **724** production checkpoints (`/Volumes/FireCuda520/ds4-kv-qwen`):

| bit | name | files | share |
|---|---|---|---|
| 0 | `TOOL_MAP` | 724 | 100 % |
| 2 | `THINKING_VISIBLE` | 38 | 5.2 % |
| 4 | **`VISION`** | **1** | 0.1 % |
| 5 | **`TOKFP`** | **724** | **100 %** |

Raw values `0x21 x685`, `0x25 x38`, `0x31 x1`. The `0x31` file was validated rather than trusted:
`sha1(stored text) == filename` **passed**, so it is a genuine checkpoint with bit 4 set, written by
`ds4_server.c:11815` (`#define KV_EXT_VISION DS4_KVSTORE_EXT_VISION`).

Consequences, in order of seriousness:
1. **The stamp parser governs 100 % of the cache** — every file claims bit 5, so `a1f3bd2` is on the
   reuse path of every checkpoint, not a subset.
2. **The fork and PR #1343 both allocate `DS4_KVSTORE_EXT_VISION = (1u << 4)`** (confirmed at #1343 head
   `fffc283` by reading the file from the API, not from memory). Upstream's #1343 does **not** define
   bit 5 at all. So a merge does not merely conflict textually — it makes bit 4 *ambiguous between two
   incompatible on-disk trailer encodings*, and 1 file already carries it. A fork binary reading a
   #1343-written cache would treat a vision section as fork-vision and skip validation of it, or vice
   versa, silently.
3. Therefore any merge of #1343 requires **choosing one vision-in-disk-KV representation** and reallocating
   a bit (bit 1/3/6/7 are unused by the fork's writers; bit 1 and 3 are taken by
   `RESPONSES_VISIBLE`/`SESSION_TITLE`), plus a migration for files already stamped with bit 4.
   Do not let this be resolved by whoever notices it first during a merge.

doc comment says *"The out-params are populated only when all three are supplied, so a caller that strips
before its own parse can pass NULL for all of them"*, and the inner wrapper ends
`…, recovered_out, NULL)` — a NULL for the *last* parameter. Both describe the degrade helper, not the
production parse. **Lesson: reading a doc comment or a wrapper signature is not evidence about a call site.
Open the call site.**
