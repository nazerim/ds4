## 8. #1020 port investigation (user asked: investigate, not do)

**Question:** can `a1f3bd2` be ported onto PR #1020 (head `9cbf7e5`, verified still open/clean at the
time of writing) so the PR's own store path stops laundering?

**A literal cherry-pick is unworkable — measured, not guessed.** `git cherry-pick -n a1f3bd2` onto
`9cbf7e5` fails outright: `rc=1`, conflicts in **all three** files, **9 conflict hunks** (6 in
`ds4_kvstore.c`, 2 in `ds4_server.c`, 1 in `ds4_kvstore.h`). The mismatch in scale is the real argument:
`a1f3bd2` carries **+1133/−31** while the PR itself is **+177/−3** on a 3-file diff. The fork tree has
**47 commits** touching `ds4_kvstore.c` between the merge base and `a1f3bd2`; the file is 1393 lines at
PR head vs 4296 in the fork. Nobody should review a 177-line PR that way.

**The minimal correct shape is ~30 lines, and the PR already has what it needs.** The store function
`ds4_kvstore_store_live_prefix_text` **already takes `ds4_engine *engine`** at PR head (line 930), so
the current fingerprint is computable at the reuse site with no plumbing. A port is an *extraction*:
1. lift the PR's inline load-side stamp read (`ds4_kvstore.c:1283-1318`) into a path-based helper
   returning a three-state verdict (our `ds4_kvstore_existing_stamp_verdict(path, cur_fp)` is the model);
2. call it in the reuse shortcut (`:1003-1006`: compat → `kv_cache_rewrite_trailer` → `return true`, the
   site with no stamp check) and take the normal staging/atomic-replace route on anything but MATCH.

**The trap a naive port walks straight into:** the PR's `kv_cache_existing_compatible` **`unlink`s the
file when it judges it incompatible**. A fingerprint mismatch is *not* the same kind of incompatibility
as a wrong-model file: deleting on mismatch destroys the self-healing path, because the next store rewrites
a correct checkpoint whereas an unlink costs a full cold prefill every time until one succeeds. Our fix
refuses reuse and **keeps** the file for exactly this reason, and distinguishes UNREADABLE (unverifiable)
from MISMATCH (verified stale). Any port must preserve that asymmetry or it trades a correctness bug for
an availability one.

**Also verified: the PR's load-side positioning is correct.** Its read seeks to `payload_start +
payload_bytes` where `payload_start = ftell(fp)` is taken *after* the text `fread`, i.e. it lands past
text+payload — the same place our parser lands. So this is a store-side gap only; do not "fix" the load path.

**Recommendation:** keep reply 2 as staged — it discloses the gap and offers the fix — and **do not
preemptively push a port**. Publishing an unrequested ~30-line rework of a reviewer's own PR into a
thread the maintainer has not read is a large action for no demonstrated gain, and the offer costs one
sentence to redeem later. Revisit only if `emilianbold` asks for it.
