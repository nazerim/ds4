# PR antirez/ds4 #1163 — rewrite vs withdraw

Coordinator-authored (inline). Three delegated attempts on this item returned no usable output;
evidence below was gathered and control-checked in the main session, not inherited.

**Verdict: `rewrite`.** Deciding criterion: **self-containment is satisfiable** — the fork's
stronger fix depends on exactly **one** fork-only symbol (`strip_dsml_keep_prefix`), so retiring a
PR that describes a strictly weaker design costs one helper port, which is cheaper than leaving a
wrong-but-open PR describing behaviour we do not run.

Marker-position difference the PR does not handle: with the envelope opened **mid-text** and never
closed, deferral alone still hands the client the raw marker text as content; the fork strips the
prefix and re-parses, so the client gets the prose plus `finish_reason: "stop"`. At end-of-turn the
two converge (nothing after the marker to recover).

## 2. Why rewrite rather than withdraw

Symbol audit — upstream vs fork occurrence counts (`git grep -c … -- '*.c' '*.h'`):

| dependency | upstream | fork |
|---|---|---|
| `tool_parse_failure_recovery_finish` | **2** | 3 |
| `parse_generated_message_ex_for_syntax` | **19** | 21 |
| `server_model_syntax` / `SERVER_MODEL_SYNTAX_DEEPSEEK` | **17 / 25** | 18 / 30 |
| `tool_calls` | **380** | 399 |
| `strip_dsml_keep_prefix` | **0** | 13 |

Controls: `SERVER_MAX_IMAGES` upstream = 7 (>0, probe reports positives); `zz_nope_sym` = 0 (cannot
fabricate hits). So the single zero above is a real absence, not a broken grep — and it is the only
fork-only dependency. The rest of the fork's mechanism is built entirely on symbols upstream already
has, including the recovery-finish mapping the PR itself leans on: the fork is a superset of #1163,
not a different philosophy.

Withdraw would be right if the port needed the DSML layer generally (it would drag in DeepSeek
marker handling upstream may not want). It does not: the strip is one call, removable at the call
site, and the degrade+re-parse behaviour is still a strict improvement without it.

## 3. Text to use

**New title:** `server: degrade an unterminated tool call to assistant text instead of faulting the turn`

**New body:**

> ## Problem
>
> When the model opens a tool envelope and never closes it before the stop token, upstream sets
> `finish = "error"` (`ds4_server.c:14390-14393`). Because the parse-failure recovery refuses to run
> when `finish` is already `"error"`, the turn surfaces as a server fault in every API shape:
> `finish_reason: "error"`, and the raw marker text is what the client is handed. A truncated tool
> call is a model-quality outcome, not a server fault.
>
> ## Change
>
> At the unterminated branch, degrade the turn instead of erroring it:
>
> - `degrade_unterminated_tool_call()` returns false unless `saw_tool_start && !saw_tool_end`, so
>   nothing changes for requests with no tools, for completed calls, or for genuine faults — the
>   enclosing guard still excludes `finish == "error"` and `"length"`;
> - map the finish reason through the existing `tool_parse_failure_recovery_finish()`;
> - drop any partially parsed call (`tool_calls_free`) and re-parse the generated text with
>   `parse_generated_message_ex_for_syntax()`, falling back to the whole text as `content`, so the
>   client receives assistant prose with `finish_reason: "stop"` and no executable half-call;
> - clear `err` only on this path — a real fault keeps its message.
>
> Deliberately not included: the DeepSeek marker-prefix strip our own build applies before
> re-parsing. It depends on DSML-specific handling that does not belong in this change; without it
> the marker text simply remains in `content`, which is the same as today's behaviour minus the fault.
>
> ## Tests
>
> Six cases in the server unit suite (`make test-server-logic`), DeepSeek and Qwen syntaxes, each
> direction: envelope opened and unclosed → degraded to text with the recovered finish; envelope
> closed → not degraded; no tool start → not degraded; `finish == "length"` preserved.
>
> ## Notes
>
> Distinct from #1355, which is about the SSE layer emitting the stream tail when the final parse
> finds no call; this is the generator deciding the turn is not a fault. They touch different
> functions and should compose.

**Code changes required to make the PR match the fork** (function-by-function, no patch binary):
1. Port `degrade_unterminated_tool_call` (`ds4_server.c:7401-7431`) **minus** the
   `strip_dsml_keep_prefix(text)` line; keep the `7408` guard, the finish mapping, the `err` clear,
   the `tool_calls_free`, the re-parse and the content fallback.
2. Replace the `finish = "error"` branch at `ds4_server.c:14390-14393` with the fork's call-site
   shape (`17179-17190`): warning log + `degraded_unterminated = degrade_unterminated_tool_call(...)`.
3. Move the fork's 6 tests (`23073-23161`) into the suite upstream's build actually compiles for
   `ds4_server.c` — in this repo that is `make test-server-logic` → `ds4_server_test`;
   `./ds4_test --server` links `ds4.c` and does **not** cover server code.
4. Drop the current PR's `test_incomplete_tool_call_keeps_stop_reason`, which asserts the weaker
   (deferral-only) behaviour.

## 4. Mention #1355?

**Yes, one sentence** (included above). Both PRs are about a tool-call marker in generated text, so a
maintainer reading them together will otherwise assume duplication; the layers differ (generator
finish decision vs SSE tail emission) and saying so in one line costs nothing.
