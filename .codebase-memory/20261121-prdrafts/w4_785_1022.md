### Why `--force-with-lease` on a PR branch is acceptable here

The project rule forbids force-pushing `main`, and this is not that case:

- `main` is the shared integration line; rewriting it invalidates other people's
  clones and every commit built on the old tip. `fix/disconnect-detection` is a
  single-purpose fork branch whose only consumer is PR #785. I verified with
  `git ls-remote nazerim refs/heads/fix/disconnect-detection` that it is the only
  ref we are moving, and the PR is cross-repo (`head_label: nazerim:fix/disconnect-detection`),
  so nothing in `antirez/ds4` can point at it.
- Nothing is lost from GitHub's side either: the pre-rebase head `2911bfc` stays
  permanently reachable through the PR's commit list and `refs/pull/785/head`, so
  the rewrite is reversible by anyone, including us.
- `--force-with-lease` with the pinned SHA makes the push fail loudly rather than
  silently clobbering a commit someone else added in the meantime.

What could still be lost, and its actual size here:

1. **Someone else's push landing between our fetch and our push** — prevented by
   the pinned lease (and by the `git rev-parse` check above). This is a live
   possibility, not a hypothetical: `maintainer_can_modify` is **true** on #785, so
   a maintainer can push to our branch. Re-check
   `git ls-remote nazerim refs/heads/fix/disconnect-detection` immediately before
   pushing and re-lease against whatever it now says.
2. **Review/discussion anchors** — inline comments attached to the old diff get
   marked outdated, and approvals/status checks reset on force-push. Cost here is
   **zero**: I verified 0 reviews, 0 inline review comments and an empty
   `statusCheckRollup` on #785.
3. **Accidentally shipping a bad rebase** — this is the real risk, and it is what
   the verification block is for. A silent "theirs"-conflict resolution on a
   432-commit gap is far more likely to lose content than the force-push is.

### Post-rebase verification — and a correction to the stated claim

**The claim as given is wrong, and inverted.** `git diff <old-head> <new-head>`
compares two *trees*, not two patches:

- `2911bfc`'s tree = base `b0a147a7` + the PR's patch.
- `NEW`'s tree = base `b3f50180` + the PR's patch.
- Therefore `git diff 2911bfc NEW` = (everything upstream changed across those
  432 commits, ≥300 files, `ds4_server.c` alone +4222/−570) plus the PR's own
  lines where they interact.

It is empty **only if the new head does not contain the upstream changes** — i.e.
exactly a broken rebase. So that check reports failure on a correct rebase and
pass on a destroyed one. The correct checks, in order:

```sh
# 1. The canonical one: same patch, different base?
git range-diff "$BASE...$OLD" origin/main...HEAD
#    expect: 1: 2911bfc = 1: <NEW>  fix: detect client disconnect on plain FIN...
#    "=" means byte-identical patch. Any "!" means the rebase changed the change:
#    stop, re-resolve, do not push.

# 2. Content check, with line-number noise removed
git diff "$BASE" "$OLD"  > /tmp/pr785_before.diff
git diff origin/main HEAD > /tmp/pr785_after.diff
diff -u <(grep -v '^@@' /tmp/pr785_before.diff) <(grep -v '^@@' /tmp/pr785_after.diff)
#    expect: empty.
#    Do NOT bare-cmp the two diffs: @@ headers carry old/new line numbers, which
#    must shift in a rebase, so cmp fails on a perfectly good rebase.

# 3. GitHub-side, after the push (values verified pre-rebase today)
gh api repos/antirez/ds4/pulls/785 \
  --jq '{mergeable,mergeable_state,rebaseable,commits,changed_files,additions,deletions}'
#    expect: true / clean / true / 1 / 2 / 287 / 11
#    mergeable_state can briefly read "unknown" while GitHub recomputes — re-poll
#    after ~60 s rather than assuming failure. REST exposes mergeable_state and
#    merged_at; the GraphQL name is mergeStateStatus (gh pr view --json
#    mergeableState is not a field and errors).

# 4. Behaviour, not just text — the PR ships its own regression test
python3 tests/live_disconnect_test.py       # needs a locally built server
```

Step 4 has a repo-specific constraint: the live test wants a server, and the
engine holds a process lock, so it runs only with the engine stopped per the
runbook (`./ds4-server.sh stop` → test → `start-qwen`). That is the coordinator's
