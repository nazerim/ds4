## Bimodal prefill (the key performance finding)

- **Large first-time prefills use the wide-batch streaming path: 550-785 t/s.**
  256k-class context is fully usable cold (~5.4 min full window).
- **Small/medium prefills (<= ~36k remainder) run the per-token streaming
  path: ~60 t/s.** A cold 2.3k prompt took 37 s. This is the chat-append
  path and dominates per-turn latency for short additions.
- **Decode: 6-10 t/s steady** — matches the engine's own Mac streaming table
  (docs/SSD_STREAMING.md: GLM 11.9 t/s, Vision-Exp 11.9 t/s); V4.1 adds
  per-token Engram disk reads. Slow but documented.
- perf_time_ms in usage excludes streaming I/O wait — use wall time.

## KV-cache policy observations

- `cold_max=30000` is real: prompts > 30k are one-shot checkpoints, never
  reused (144k rerun: cached=0, same 4-minute prefill). Chat-sized prompts
  keep anchors (8k rerun hit cached=8192; multi-turn turn2 hit cached=42).
- One 2286-token checkpoint consumed on one load then missed next identical
  rerun (cached=0 after cached=2048) — anchor lifetime oddity worth a look
  against PLAN-KV docs if it shows up in real traffic.

## Verdict

256k context on SSD streaming **works** and is the shipped default now.
Interactive latency is the streaming tax: fast on big fresh prefills,
acceptable on anchored continuations, sluggish for medium cold appends.
Best fit right now: long-running agent sessions with disk-KV anchor reuse
rather than snappy chat. If per-turn latency matters more later, the
resident 512 GB path or two-host TP is the documented upgrade.

**No flag differentiated.** C2≈C3≈C4 within noise; the 4x gap to C1 was
pre-existing engine STATE, not configuration. Additional eliminations:
- Page-cache purge test (165 GiB bulk read evicting Engram pages, no restart):
  decode UNCHANGED at 22.7 t/s -> page cache is NOT the degradation axis.
- Remaining suspect: expert-cache working-set contamination by high-entropy
  content (random-hex/CJK/JSON variety runs preceded C1's 4.6 t/s).
- **CONFIRMED**: 337k contamination tokens (123k random-hex + 48k CJK + 165k
  JSON) dropped decode 22.7 -> 10.6 t/s (tiny-turn wall 4.5 -> 9.8 s) - and
  it RE-CONVERGES: next call already 15.9 t/s / 6.0 s. Remediation is simply
  letting the working set settle (a few turns); a restart only speeds that up.
- **CORRECTION (live opencode session, 1h continuous agentic traffic)**: it
  does NOT settle under sustained churn. Decode decayed monotonically
  12.4 -> 10.4 -> 5.0 -> 3.9 -> 3.4 -> 3.1 t/s across 07:40-08:47 while every
  turn appended tool results + reasoning. System healthy throughout (swap
  flat 834 MB, free 23%). The earlier "self-heals" result only held because
  traffic paused between probes. Floor under continuous mixed traffic: ~3 t/s
  = ~4-5 min per 1k-token turn. Restart is the only reset for a long session.
- CJK prefill reproduced at 48k: 141.7 t/s (vs 540+ prose/code/json at
  similar scale) - content-dependent 4x prefill tax for CJK, likely Engram
  access pattern. Multilingual agent traffic should budget for this.

## Live-session mechanism: small appends run ONE TOKEN PER STEP (2026-11-07)

Live opencode session confirmed the append slowness and its mechanism
(source trace: ds4.c `ds4_session_sync_internal` -> `ds4_session_is_ds41`
loop, ~80877; `ds41_prefill_count` ~43517):

- V4.1 SSD-streaming continuations choose a step size per sync iteration.
  On this build the decision chain is: batched short rows
  (`ds41_graph_short_prefill`) are **CUDA-only** — `ds41_cuda_row_batch_supported`
  is hard-`false` on Apple — so `short_count=0` always on macOS.
- `ds41_prefill_count`: streaming + `pos>0` + `expert_cache_configured_count
  >= N_LAYER*N_EXPERT/2` raises the batching floor `minimum` to **1024**.
  Boot log: cache = **8577 expert slots**; V4.1 total = 40x384 = 15360;
  half = 7680 -> condition holds ALWAYS (slots configured, not live hotness).
- Appends below the floor return count=1 -> `ds41_graph_step` per token:
  full 40-layer forward per token, and one `prefill_chunk` progress event
  per token -> one log line per token (observed: 551 tokens = 551 lines,
  strictly +1, 7.04 t/s, 79 s).

Cliff: continuation append <1024 tokens -> token-major (~7 t/s on novel
routing, ~15-23 warm); >=1024 -> batched layer sweep (~400-700 t/s). A
900-token tool result costs ~130 s while an 1100-token one costs ~2 s.
Root economics: 6+1 experts/layer read per token = up to 2.66 GiB of expert
streaming per token at 9.49 MiB/expert; the layer sweep amortizes expert
reads over all tokens, token-major pays them per token. Tool-result JSON
routes outside the warm working set -> ~55-60% miss -> 142 ms/token.
Matches the contamination finding (same axis, same self-healing).

Log-line cost: `server_log` -> unbuffered `fprintf(stderr)` = one write()
per line, no fsync: ~5-15 us -> ~3-8 ms per 551-line append (~0.01% of the
79 s). The per-token log is the SYMPTOM, not the cost. No env knob exists
to batch sub-1024 appends on Mac (DS4_METAL_DISABLE_V41_LAYER_PREFILL
goes the other way); candidate upstream request for antirez/ds4: gate the
1024 floor on actual cache hit-rate/content, or enable short row-batch on
Metal, or add an env override.

## DSpark A/B on V4.1 SSD streaming: FALSIFIED (2026-11-07)

Built + verified the drafter (gguf/DeepSeek-V4.1-Flash-DSpark.gguf, 81/81
tensors match pinned df42c109 checkpoint), wired `restart-v41-dspark`
(gate self-tested), ran ~3 h of real agentic traffic (opencode session,
DSML tool calls, ctx 58k->142k):

- Decode curve vs plain same-day run: 15.7 fresh -> 4.9 @1h -> **2.3 floor**
  vs plain 12.4 -> ~5 -> 3.1. Identical contamination shape, WORSE floor.
- Mechanism of the extra loss: 43 `route=truncation` generation rewinds in
  3 h - every DSML tool-call turn pays a rewind/replay (+ exact-sampling
  resample replay), each replayed token = full SSD expert-streaming step.
- Drafter also costs 5.5 GiB of expert cache (79.51 -> 73.96 GiB), speeding
  up contamination thrash.
- DS4_DSPARK_STATS=1 produced no accept-rate lines in-session (printed on
  session release; SIGTERM skips it).
- Matches upstream doc caveat: "V4.1 DSpark can still be slower than
  ordinary decoding". Rollback lever: plain `restart-v41` (or
  DSPARK_EXACT=0 opportunistic mode - untested, would change distribution
  handling, not the rewind overhead).
**Conclusion: keep V4.1 server lane plain. dspark stays available via
`restart-v41-dspark` for non-streaming hosts / long-generation workloads.**

SUPERSEDED CONTEXT (15:20, 2026-11-08): both the dspark legs AND these plain legs ran
on a substrate with the transient-buffer leak (see
`UPSTREAM-TRANSIENT-LEAK-20261108.md`) - absolute rates are floor-poisoned, and
dspark's drain-amortization made it look artificially better as sessions aged.
Re-baseline legs (exact vs non-exact on fixed build) pending; relative policy
findings (F1/F2 null) were re-derived post-fix in `PLAN-DECODE-DEGRADE-20261108.md`.

## DSpark A/B on V4.1 SSD streaming: VERDICT REVISED (operator observation 2026-11-08)

RE-BASELINED post-transient-fix (2026-11-08 evening, termbench legs, plain vs
`restart-v41-dspark` exact). NORMALIZED metrics (decode-isolated: turns
segmented at finish=, gen/decode-wall from engine cumulative fields, prefill
excluded; the first pass polluted medians with token-major append walls, and
chunk=9174 t/s was a prefill-boundary interval artifact, not a burst commit):
  aggregate decode tps plain 22.90 vs dspark 22.37; per-turn median 22.7 vs
  22.7; plain p10 21.6 vs dspark 19.2; dspark p90 26.3 vs plain 23.8.
Verdict: NEUTRAL-to-slightly-negative for dspark (bursts real but modest; worse
floor; ~0.7 truncation rewinds/turn; -5.5 GiB expert cache). The earlier
"dspark helps real traffic" signal = the transient leak's drain-amortization
shadow (see UPSTREAM-TRANSIENT-LEAK-20261108.md). DEFAULT LANE: plain.
Synthetic soak legs (dspark_base/dspark_noexact) had shown the same neutrality.

THREE-WAY UPDATE (termbench leg 3, `DSPARK_EXACT=0`, boot 18:15, 36 turns):
noexact wins - intervals p10/med/p90/p99/max = 20.2/24.3/31.3/39.5/55.0,
per-turn mean 24.2 vs 22.0 for BOTH plain and exact. Verdict refined: dspark
IS faster on coherent real traffic (+9-10%), but only in opportunistic
(non-exact) mode; the exact-sampling correction rule consumes the entire
acceptance gain (exact: median -0.7, p10 -1.9 vs plain). Operator's original
"dspark helps" observation = leak shadow + interval artifacts, NOT speculation.
THIRD-WAY RETRACTION (19:15, stats probe): ds4_session_dspark_stats_begin/line
landed (DS4_DSPARK_STATS=1 now prints per-request 'dspark req:' deltas) - and
proved cycles=0 proposed=0 on the SERVER for V4.1 with full dspark flags
(+--mtp-draft 5). Server single-slot never enters the speculative impl
(non-batched branch gated by dsml_token_id<0 - impossible on DSML models;
batched mode docs: other models do not use MTP/DSpark). All termbench legs
were plain decode with a drafter loaded; the 3-way "noexact wins" row is
retracted (p90 tails = warm-cache noise, bursts = interval straddles).
REPL proof unaffected: engine V4.1 speculation works (cycles=120,
accept 66.1%) - the server loop is the gap. Follow-up: wire ds41_session_speculate
into the single-slot loop (small, dispatch already exists at the impl's
90405) or document the server lane as plain-only.

Original falsification above was taken mid-session at 138-142k context during
warm-up (rewind storms, 2.3 t/s windows). Overnight log (rotated 20261108-051511)
shows the STEADY-STATE behavior: late-session decode chunk rates min 3.9 /
