# FLOOR-20261001 — the per-store fixed floor, measured properly

Replaces the handover item-4 claim ("one store of a 248-row delta cost
862 MiB — maybe a ~0.8 GiB floor"). The earlier aggregate was garbage
(broken awk field split on `..`); this pass parses `delta=A..B` endpoints
with a verified regex against the verified line format
(`stored tokens=… trimmed=… reason=… key=… sha=… [delta=A..B] size=X MiB
save=Y ms`), 444 stores across `log/ds4-qwen.log*`.

## The floor, explained by code

`qwen4_session_save_payload_span` (ds4.c ~62890) writes
`payload_write_tensor_span(fp, g->layer_lin_state[il], 0, …state_bytes…)`
and the conv history for **every linear layer**, offset 0, full size,
independent of `rows_from` (same for `ple_hist`).

With lin_state = 48×128×128×f32 = 3.000 MiB and conv hist = 0.117 MiB per
linear layer:

    per-store GDN/PLE fixed floor ≈ 36 × 3.117 MiB ≈ 112 MiB (+ ~1.3 MiB
    logits/ple_hist ≈ 113.5 MiB total fixed)

This lands exactly in the measured band (97–175 MiB floor).  The delta
`size=` is therefore `~113.5 MiB + rows×~30.7 KiB + text/trailer` — the
"rows" term dominates for ladder stores; the fixed floor is the price of
each frontier store regardless of span.

## Findings

1. **The hard per-store fixed floor is ~97–175 MiB, not ~0.8 GiB.**
   Five identical cold stores: span=2048 → **175.1 MiB** each (every time).
   Continued ladder: span=4096 → 236.7, span=6144 → 298.2 (Δ=61.5 MiB per
   2048 rows → **~30.7 KiB/row marginal**, floor ≈ 236.7−61.5·2 = 113.7).
   The `size=` field is exactly `fixed + text + payload + trailer`
   (ds4_kvstore.c:2058-2068) — there is no hidden per-file rounding cost.

2. **The 862 MiB / 248-row datum was REAL but is NOT the floor.**
   Small-span (<8k rows) `evict`/`shutdown` stores from long sessions
   (tokens ≥ ~130k) run 580–1260 MiB:
   `294912..295160=862`, `364708..366746=1095`, `376832..382971=1259`,
   `360448..364708=1157`, `131072..135487=586`, `196608..200880=746`.
   The same small spans in young sessions (tokens < 70k) stay 196–399 MiB.
   Mechanism (verified): the span writer emits full GDN linear state +
   PLE history per store (see "The floor, explained by code" above) —
   ~140 MiB fixed; the additional hundreds of MiB that scale with session
   length sit in fields not yet fully decomposed (mtp_rows window,
   per-layer attention tensors beyond the KV span).  That residual is the
   open question, not a flat 0.8 GiB floor.

3. **Consequence for the "skip frontier stores below a minimum span"
   idea (handover item 4's motivation):** the per-store floor is ~100–175
   MiB, not ~0.8 GiB, so skipping sub-minimum-span stores saves ~0.1–0.2
   GiB per skipped store — a rounding error against the ~113.6 GiB/run
   ladder (326 continued stores × ~35 KiB/row is where the real volume
   lives). The P2.1 "stay deferred" decision does not change.

4. **The open optimization (not a floor):** long-session evict/shutdown
   stores pay 0.6–1.3 GiB for a few-thousand-row delta span. The 140 MiB
   GDN floor explains the fixed part; the span-length scaling part needs
   `qwen4_session_save_payload_span` decomposed field-by-field (mtp_rows,
   attention tensors) before any "cap staged rows" change is safe.

## Method notes (for the next reader)

- Parse from log lines with `delta=(\d+)\.\.(\d+)` capture groups — the
  handover's awk split on `.` produced the "862 MiB floor" reading.
- 395 vs 444 store counts differed between two parse attempts; the
  endpoint-capture parse (444) is the correct one — the first used a
  whole-`delta=` optional group that silently failed.
- Model-free; no engine interaction; engine stayed live throughout.
