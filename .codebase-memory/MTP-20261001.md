# MTP-20261001 — why long-session stores pay +2.6 KiB per token (the 0.5–1.1 GiB extra)

Resolves the open question left by FLOOR-20261001 (handover item 4).

## TL;DR

Every Qwen3.8 session store — including small delta spans — copies the
**full MTP-block (nextn) history from row 0**, i.e. `mtp_rows == rows ==
the entire live session length`. For a 295k-row session that is
`295160 × 2.58 KiB ≈ 741 MiB` written **per store**, regardless of whether
the store's own delta span is 248 rows or 16384.

## Evidence

1. **Empirical fit** (390 stores, headers + logs cross-checked; all
   `delta_from` fields verified against the log line, 390/390):

   - `evict`:     size = 113 MiB + 30.8 KiB×span + 2.58 KiB×tok   (medres **1.2 MiB**)
   - `shutdown`:  size = 101 MiB + 30.8 KiB×span + 2.62 KiB×tok   (medres 5.3 MiB)
   - `continued`: span+tok fit has medres 145 MiB → the tok term is *not*
     universal (see nuance below).

2. **Header field** — payload `mtp_rows` (u32 after logits):
   `f454de7b`: rows=212992, MTP_ROWS=**212992** · `d4c84884` (the 248-row
   store the handover quoted): rows=295160, MTP_ROWS=**295160**.

3. **Code** — `qwen4_session_save_payload_span` (ds4.c ~62849):
   `const uint32_t mtp_rows = g->mtp_pos < rows ? g->mtp_pos : rows;`
   with the comment “MTP history is small and tracked by its own row
   count; **P1 copies it whole** so delta chaining only needs the main
   rows.” `g->mtp_pos = idx + T` (ds4.c:59132/59207) tracks the committed
   length, so in normal sessions `mtp_pos ≥ rows` → `mtp_rows = rows` →
   the "small" history is actually the whole session.

4. **Size arithmetic**: 2×kv(256×2×2) + ik(4×128×4) + bk(4×128×2) = 2688 B
   ≈ **2.625 KiB/row** — matches the fitted 2.58–2.62 KiB×tok exactly.
   (The handover's famous 862 MiB datum: 2.625×295160 ≈ 758 MiB of MTP +
   113 MiB fixed + slice ≈ 862 MiB. Mystery closed.)

## Nuance (why continued stores sometimes don't pay it)

The tok-term appears only where the store's `rows_from`/resume state
leaves `mtp_pos` unclamped to the span. Continued stores that chain from
a parent and were loaded via `qwen4_session_load_payload_span` (which
sets `g->mtp_pos = mtp_rows`, ds4.c:63032) inherit the FULL mtp_rows of
the parent and keep re-writing it — so long chains re-copy MTP at every
link. The fit's large continued-store residuals (up to 662 MiB) are the
sessions whose parent chain already carried a bloated MTP.

## Cost

Per store ≈ `2.625 KiB × session_rows`. Production run (~113.6 GiB, 326
continued stores, sessions 60k–450k rows): the MTP whole-copy is on the
order of **100–250 GiB/run of pure duplicate history** — every store
rewrites the same MTP rows its ancestors already stored.

## Fix (NOT implemented — decision needed)

Slice nextn exactly like the other attention layers:
`k_off=qwen4_payload_kv_bytes(rows_from) …` (and `ik_off`/`bk_off`), and
persist `mtp_rows_from` so the loader can restore into the right offset.

Risks/requirements:
- ABI: needs a version/ext-flag bump (old loaders read nextn at offset 0
  and would mis-slice new files; new loader must handle old whole-copy
  files).
- Loader (`qwen4_session_load_payload_span`) + full store path stay
  compatible: full stores keep rows_from=0 → whole copy → unchanged bytes.
- `mtp_pos` after resume must be restored as `rows_from + stored_rows`
  semantics, with the rewind guard extended (graph position vs mtp).
- Test: model-free harness can't exercise GPU tensors; verification needs
  a live qwen store/load round-trip (engine test, cannot run alongside
  the live server).

Given the engine is live and the standing constraint (no model-backed
tests while it runs), implement behind the next planned restart window,
or gate on `DS4_KV_MTP_SLICE=1` env for a controlled trial.
