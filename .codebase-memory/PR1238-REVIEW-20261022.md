## What it does (decode-side, T==1 restructures on M5)

- hc_norm 8-way / inject-partials 16-way / attn-merge maxima 16-way staged
  reductions; attention NSG 4/HPS 3 -> 6/HPS 2 (compile-time).
- IQ2_XXS grid/sign tables staged in threadgroup memory (new
  kernel_qwen4_moe_mid_iq2xxs); Q2_K row-dot word-loads; fused
  down+reduce (kernel_qwen4_moe_down_reduce); BF16 router matmul when the
  F32 router row is BF16-exact; hc_norm next-layer prefetch; PLE n-gram
  staging moved after layer-0 flush (overlap) + extra mid flush.
- Claimed: decode 48->54-56 t/s (+10-17%), bit-exact logits gated (112
  teacher-forced rows, 2 fixtures) — but no shipped tests; per-commit A/B
  JSON only in commit messages.

## Bit-exactness verdict (from code reading)

Order-preserving everywhere examined; the attention NSG/HPS change is
provably safe (each q-head is owned by ONE simdgroup; no cross-group
reduction; capacity identical). Riskiest spots: Q2_K word-load alignment
assumption (verified correct, silent-corruption class) and the BF16 router
(exact iff the T==1 router gemv takes the plain-mv path — triple-pin
settles it). PLE overlap is scheduling-only (exact by construction) but
changes the failure-consistency envelope of ngram reads mid-forward.

## Caveats against OUR production

- Benchmarked on **Q2**; our production is **Q4** — IQ2_XXS mid, Q2_K
  word-loads, down-reduce fold, M5 type-16/10 specialize are all INERT on
  Q4. What will run here: attention NSG/HPS + merge staging, hc_norm/inject
  staging, F32 row-dot unroll, BF16 router, PLE overlap, hc prefetch — most
  of it unmeasured upstream.
- Prefill regression **-4..-7% at >=14k** (author admits, investigating) —
  caused by the PLE flush split, which has NO kill switch (fork's analogous
  overlap honors DS4_QWEN4_NO_NGRAM_OVERLAP). Attention NSG change is
  compile-time only (no runtime revert).
- Zero shipped tests — validation is entirely ours.
