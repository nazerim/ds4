# THINK-20261001 — "thinking not closed, ignoring incomplete Qwen tool calls in reasoning"

Reviewed end-to-end. **Verdict: expected upstream behavior, very low real
rate, one cosmetic log-hygiene nit. No engine fix needed. Do not confuse
it with the unterminated-tool-envelope upstream draft PR (see §4).**

## 1. Not a fork artifact

All three variants (DSML / GLM / Qwen) exist verbatim on `origin/main` —
Qwen variant from `ccea768` "Add Qwen3.8 Flash Next model support". The
fork does not modify this block.

## 2. Trigger condition (ds4_server.c ~6772, Qwen path)

When `require_thinking_closed` (thinking-mode response) and the generated
text has NO closing think-tag and NO complete tool envelope, the server:
- logs this message to stderr,
- calls `ds4_local_unterminated_reasoning`: raw text goes entirely to
  `reasoning_content`, `content` becomes empty string,
- returns normally; the turn finishes with its existing finish_reason.

## 3. Why it looked alarming today

Rate in real traffic: 1 occurrence per 660 generations (0930 20:19 →
1001 09:18 boot), and 0/312 the boot before — negligible. Today's three
occurrences were all MY synthetic test probes: tiny max_tokens budgets
(24–120) with temperature 0 — every generation ends `finish=length`
mid-reasoning by design. A `finish=length` truncation of reasoning always
fires this message. It is the intended conservative handling: half-formed
tool envelopes cannot be executed, and per the 0926 confabulation
decision, reasoning truncated at max_tokens must not be rewritten into
content.

## 4. Distinct from the upstream draft PR (UPSTREAM-PROPOSALS-20260929)

The draft PR targets a different branch: the model *did* open and close a
tool envelope in visible text but it failed to parse, and the turn was
classified `finish=error` instead of degrading to assistant text. This
message's path never sets error; it degrades reasoning→content to empty.
Same family (unclosed model output shapes), different code, different
client-visible outcome.

## 5. One real nit (optional fix, fork-side)

The message fires even when NO tool call was present at all (plain
reasoning truncated at length) — `!candidate || !strstr(tool_end)` enters
the same log line for "no tool started" and "tool started but unterminated".
Consequence: stderr noise proportional to length-truncated reasoning, and
the only case where a real tool call is silently dropped is
indistinguishable from benign truncation. If we want it: gate the message
on `candidate != NULL` (i.e. tool_start present), or demote to
DS4_LOG_KVCACHE-style debug. No correctness change. Not done — flagged
for the next time we touch the response path.
