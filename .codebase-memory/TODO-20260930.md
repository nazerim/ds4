## 1. P2.1 middle-retire re-anchor — DECISION PENDING ON EVIDENCE

**What it is.** Delta chaining requires `parent.tokens == child.delta_from`, verified
by re-reading the parent header. So a checkpoint in the middle of a chain (parent +
exactly one child) cannot be deleted without orphaning the child; the policy defers
instead (`kv cache delete deferred reason=redundant children=1`). The node is dead —
nothing restores from it, the child supersedes it — but its bytes stay pinned while the
child lives. P2.1 = re-anchor the child onto the grandparent (read the interior span,
rewrite the child's delta to start there), then delete the interior node and reclaim
its bytes. It is the ONLY change in the fork that would mutate an existing checkpoint.

**Why it was deferred.** Evidence at decision time: 4 deferral lines across all logs,
zero exceeds-budget events, deepest resume 416088 tokens in 2881 ms against a 10 s
threshold.

**Why the decision is open again.** Two of my own trigger metrics have since moved:
a single startup scan now emits **123** deferral lines (vs 4), and reclaimable is
**180.1 GiB in 255 files** on a blade measured at 508.9 / 512 GiB.

**Counter-evidence — do not build yet.** The ladder fix (3133d86) changed the
economics. Before: frontier stores chained from 131072 at ~5,500 MiB, save ~2,000 ms.
After: they chain from the last rung at **296 MiB, save 85 ms** (measured live:
`tokens=66088 reason=evict delta=65536..66088`). Write volume is roughly 18x lower, so
much of the 180 GiB is legacy fat stores and v2 objects (92 files / 246.7 GiB, which
predate chaining and cannot chain at all). Also note the uncomfortable half-truth: the
ladder creates MORE interior nodes, so deferral volume rises because the fix works.

### Collect over 2–3 days of normal sessions, then decide

1. **Reclaimable split — the deciding number.** Of the interior nodes, how many bytes
   belong to a LIVE lineage (a session resumed from that chain recently) versus DEAD
   (superseded, never read again)? Dead weight that ordinary conversation-retirement
   already reclaims means P2.1 buys little; live-pinned bytes mean it is needed.
2. **Deferral trend** per day: rising curve = build it; flat = leave it.
3. **Occupancy trend**: stable near 509/512, or climbing? Stable means the fix already
   relieved the pressure.
4. **Do interior nodes die with their conversations?** If retiring a conversation
   reclaims its whole ladder, the self-cleaning path is enough. If interior nodes
   outlive their own conversations, that is exactly the P2.1 gap.
5. **Chain depth** (was 28 hops): rungs every 16k tokens make depth grow with session
   length; deep chains are where deferrals concentrate.
6. **exceeds-budget events**: still zero = no urgency; nonzero = trigger fires now.
7. **Resume latency**: if deep chains push loads toward the 10 s threshold, shallower
   chains matter for latency, not just space.

**Commands.** `python3 tests/kv_blade_census.py` (reclaimable + by-reason, correct map
since ecccc83); `python3 tests/kv_chain_ancestry.py` (chain walk, birth times — NOT
mtime, which the hit path touches on read); `python3 tests/kv_store_existence.py
<logs>` (logged store vs file present).

**If it is built.** Re-anchor must be atomic and verified: a half-finished rewrite
corrupts a live lineage rather than merely wasting space. Prefer tmp-file + fsync +
rename + header re-verify, and keep the existing fail-closed rule (no verified
ancestor ⇒ write full).

**Cheaper levers to try first.** (a) Raise the 512 GiB budget — the volume has 1.1 TiB
free, so this is a policy line, not hardware. (b) Prune whole dead conversations rather
than nodes — conversation-retirement already exists and mutates nothing. (c) Re-measure
after a few days so the reclaimable figure reflects post-fix store shape.

## 2. Slot count — can we run more than 2 concurrently?

Operator observation: 2 parallel decode streams run **60–70 t/s aggregate**, better
than 50–60 t/s for a single stream. Expected: decode is weight-streaming bound, so
batching amortises the same weights across sessions.

Launcher already encodes the trade-off (ds4-server.sh:80-84): at ctx > 262144 it sets
2 slots, at 262144 it sets 8, with the comment that "512k sessions request 256 GiB of
buffers against a ~122 GiB Metal ceiling". So 2 is a deliberate memory cap, not a code
limit, and `QWEN_BATCH_SESSION=3 ./ds4-server.sh start-qwen` is the override — env only,
no rebuild.

Measured on this box right now: engine RSS **7.1 GiB idle** while its log claims
"2 resident sessions request at least 63.81 GiB" — so context buffers commit against
USED rows, not the ctx cap. Arithmetic: 31.9 GiB per 512k slot ⇒ 3 slots ≈ 96 GiB
against a ~122 GiB ceiling. Plausible on paper, untested in practice.

**Test at a quiet point (engine idle, session resumable from a shutdown persist):**
start with `QWEN_BATCH_SESSION=3`, then check the startup line "N resident sessions
request at least ... GiB", the Metal allocation result, swap (`sysctl vm.swapusage`,
currently 2305 MiB used of 3072), and per-slot decode t/s under real load.

**Know the trade before doing it.** Aggregate throughput rises, but per-slot decode
LATENCY roughly halves again at 3 streams (~20 t/s per slot if 2 slots give ~35). That
directly hits this pi setup: tool-call turns stream token-by-token. Also more active
generations means the mixed-prefill quantum interleaves more often, so long prefills
get slower again — the thing 512 was raised to fix.
