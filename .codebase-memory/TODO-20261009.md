## 1. PLAN-DECODE-HOTLIST.md — V4.1 decode-biased expert hotlist (HIGH priority)

**Problem**: Runtime hotness tracking (`g_stream_expert_cache_route_hotness`) and
profiler (`ds4_expert_profile_record`) aggregate prefill + decode expert selections
without distinction. For agent workloads (50k prefill + 5-10k decode), prefill
dominates by ~6.7x in selection count, biasing LFU eviction toward prefill-hot
experts. But decode is more latency-sensitive (sequential, exposed cache misses).

**Solution**: Gate hotness tracking on decode phase using existing
`ds4_gpu_decode_phase()`. Two env vars (default off, backward compatible):

| Env var | Effect | File:Function |
|---------|--------|---------------|
| `DS4_STREAM_HOTNESS_DECODE_ONLY=1` | Skip hotness tracking during prefill | `ds4_metal.m:14497` |
| `DS4_EXPERT_PROFILE_DECODE_ONLY=1` | Skip prefill records in profiler | `ds4.c:1687` |

**Target**: V4.1 Flash Q2/Q4 on M5 Max 128GB with `--ssd-streaming` (152/294 GiB
main weights don't fit resident). Expected 10-30% decode improvement.

**NOT applicable to**: Qwen3.8 or DeepSeek V4 Flash on 128GB (fully resident, no
expert cache eviction — hotness/eviction logic irrelevant).

**Engram tables**: V4.1 Engram (189 GiB, disk-only) is attention KV cache lookups,
NOT expert weights. Decode-biased hotlist does NOT directly affect Engram tables.
But Engram layers (1, 14) still have routed experts that benefit from the hotlist.

**Implementation phases**:
1. Add `DS4_STREAM_HOTNESS_DECODE_ONLY` env var (opt-in, low risk)
2. Add `DS4_EXPERT_PROFILE_DECODE_ONLY` env var (opt-in, low risk)
3. Generate V4.1 built-in hotlist from decode-only profile (`ds4_streaming_hotlist_flash41.inc`)
4. Make decode-only the default for V4.1 (medium risk — changes default)

**Full plan**: `PLAN-DECODE-HOTLIST.md`

## 2. PLAN-PLE-PRELOAD.md — Qwen3.8 PLE n-gram preload/cache (LOW priority)

**Problem**: Qwen3.8's 95.37 GiB PLE n-gram table (`per_layer_token_embd.weight`)
is read from disk on every token via synchronous `pread()`. No cache, no preload,
no prefetch.

**Current state** (`ds4.c:57465` `qwen4_ngram_row`):
- Every row access = `pread()` syscall
- No LRU cache, no hotlist, no OS page cache reliance (separate fd, not mmap)
- Prefill: batched with 16 concurrent readers, dedup + sort (efficient)
- Decode: 24 rows per token (1 token × 24 heads), uses `dispatch_apply` with 16 readers

**Measured impact** (from QSA-ATTRIBUTION-20261004.md):
- PLE bucket: 36 ms per 8192-token chunk = **0.63% of prefill**
- PLE bucket: 18.6 ms per 2048-token chunk = **1% of chunk**
- PLE I/O during decode: ~200μs per token = **0.6% of decode time** (at 30 t/s)

**PR #1072 evidence**: oMLX tried RAM-caching Engram hot rows — measured **22.5%
row reuse** over 600-token coding generation. Concurrency won, caching didn't.
3-gram hashing produces mostly unique rows.

**NAX analysis**: PLE GEMV (key/value projections) could use NAX, but:
- Prefill: GEMV likely already on NAX/MPP via batched path
- Decode: GEMV is memory-bound, launch overhead dominates
- Expected gain: <0.2% prefill, <1% decode

**Verdict**: **Low impact (<1%)**. Deprioritized. Keep plan for:
- Cold-cache scenarios (first run after boot)
- Slow SSD (USB, network)
- Multi-session I/O contention
- Very high decode speeds (MTP 100+ t/s)

**Upstream PR survey** (2026-10-09): No existing PRs for PLE/n-gram caching.
PR #1047 (Qwen3.8 SSD expert streaming) explicitly rejects popularity preloading
for Qwen. PR #1072 (Engram concurrency) is the closest analogue.

**Full plan**: `PLAN-PLE-PRELOAD.md`
