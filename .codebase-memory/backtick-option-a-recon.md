## f. Upstream vs fork

- **Upstreamable, not fork-specific.** The error site is upstream code: origin/main:ds4_server.c carries the identical handler and message at 14313-14359, introduced by upstream commit 759dd7c "Do not repair truncated tool actions or exceed output limits" (2026-09-06, Salvatore Sanfilippo), present on both origin/main and nazerim/main.
- Upstream already ships the parser policy (`tool_parse_failure_recovery_finish` at upstream 6777/6825) and the `recovered_tool_parse_failure` degrade block (upstream 14417+). Option A is therefore "let the unterminated-envelope branch join the policy upstream already applies to unparseable envelopes" — a consistency argument, not new design, and it removes a client-visible finish_reason "error" for a model output shape.
- Keep fork-only pieces out of an upstream patch: `strip_dsml_keep_prefix` (fork commit a171132 "fix: harden DSML recovery, add post-recovery validation and streaming fallback") and the qwen visible-checkpoint family. Upstream's degrade branch does not strip, so an upstream variant would return raw markup as content — propose either upstreaming the strip or shipping the finish change alone there (it still kills the finish=error class).
- Separately upstreamable observation: `anthropic_stop_reason` (9222) maps finish=="error" to "end_turn", so Anthropic clients never see this failure at all (they get end_turn plus raw markup as content). That asymmetry is upstream behaviour and worth reporting on its own, independent of Option A.
- Fork-side follow-up worth recording regardless of the upstream decision: risk d.5/d.7 (visible checkpoint remembered while live tokens contain stripped markup) is the only correctness hazard the change introduces, and it is a two-line gate.
