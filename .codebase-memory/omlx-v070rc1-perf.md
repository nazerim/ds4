## 2. What actually changed in the prefill path

Range v0.6.2 (f2d36f3d, 2026-08-19) .. v0.7.0rc1 (35be079d, 2026-09-25): 836 files, +205,791/−32,543. Headline is **3e2bdb1f "perf(qwen4): speed up Flash-Next prefill (#3903)"**, 18 files, +713/−105.

**(a) `omlx/patches/qwen35_gdn_prework.py` +187 — fused GDN prefill prework.** Rewrites the *verify* kernel's compile-time row constant to a runtime value so one pipeline serves every width: `uint(NKEEP - S)`→`uint(NKEEP) - S_rt`, `S < NKEEP`→`S_rt < uint(NKEEP)`, `uint(S)`→`S_rt`, prepending `const uint S_rt = uint(s_len);`. Norm-gate takes its row from `threadgroup_position_in_grid.y`: `base = (y*HV + head)*DV + lane*4`. Grid `(32, length, 2*hk+hv)`, threadgroup `(32,1,1)` — **token-parallel**. Template T=bf16, HK=16, HV=48, DK=DV=128, NKEEP=3, C=10240, L2=1. Emits q,k,v,next_conv in one dispatch, then calls stock `q35.gated_delta_update(..., use_kernel=True)` — **the chunked recurrence is not reimplemented**. No simdgroup-matrix, no ANE. Gate `_qwen4_prefill_eligible`: batch==1, rows≥64, hidden==2560, bf16, GPU, cache len 2, not speculating, no history_capacity, `lengths is None`, `left_padding is None`, conv_state (1,3,10240) bf16, recurrent (1,48,128,128) fp32. Env `OMLX_QWEN4_GDN_PREFILL_FUSED` (default on).

**(b) `.../qwen4_exp/hc_fused.py` +217 — hyper-connection prefill epilogues.** `_WN_SOURCE` (`omlx_qwen4_hc_prefill_write_norm`, grid `(256, hc, rows)`) fuses the pending residual write `y = T(x + T(branch*gate[s]))` *into* the per-stream RMSNorm, emitting new residual + normalized stream in one pass; uses `metal::precise::rsqrt` (`_NP_SOURCE = _N_SOURCE.replace("metal::rsqrt", ...)`) and rounds to bf16 after each gate/product/partial-sum to match eager. `_TI_SOURCE` (`omlx_qwen4_hc_prefill_tail_inject`, grid `(256,1,rows)`) fuses `mixed = mean_s(sigmoid(up_s)*normed_s)` with `inj = 2*sigmoid(normed·inject_row/HC)` read from the **quantized 4-row inject bank**: affine **group size 64**, `pack_factor` = 8 (5-bit) / 4 (6-bit) / 32÷bits, `ROW_BYTES = K*BP/PF`, `GROUPS = K/64`; each of 256 threads owns `PER = K/256` elements, dots whole packs, `simd_sum` → `threadgroup float part[HC][8]` → 8-way cross-simdgroup reduce. Needs `width % (256*pack_factor) == 0`. Docstring: prefill keeps down/up projections on the MLX matmul path; "FP32 epilogues can round differently from the canonical BF16 operations."

**(c) `.../qwen4_exp/language.py` +124.** (i) **QSA dense/sparse split**: rows seeing ≤ the block budget select every block anyway, so `dense_rows = min(length, max(0, token_budget + compress_ratio - 1 - past_len))`, minus 1 if that leaves a single sparse row (gathered QSA needs ≥2 query rows); dense arm → stock `mx.fast.scaled_dot_product_attention(mask="causal")`, sparse arm → `contiguous_causal_gathered_qsa`, then `mx.concatenate(axis=1)`. (ii) `Qwen4ExpGatedResidual.__call__(..., write=None)` threads the pending `(branch, gate)` write into the HC kernel instead of materializing `hyper_input + injection` (`_hc_write` = eager fallback). (iii) `ShardedEmbedding.__call__` PLE gather rewritten from a Python per-token loop (`bisect_right` + `result.at[positions].add(values)` scatter-add per shard) to numpy `searchsorted`/`argsort(kind="stable")`/`unique(return_index=True)`, one gather per touched shard, one `mx.concatenate`, one inverse-permutation `mx.take` — pure host-overhead removal.

**(d) `.../qsa_fast.py` +20** — `query_chunk = max(query_chunk, 256)` → **1024** when native `qwen4_qsa_sparse_gqa_attention` exists; a 1024-row tile keeps the FP32 score sheet small (268 MB @256K keys) while cutting per-tile dispatches.

**(e) `omlx/scheduler.py` +43** — `_QWEN4_WIDE_PREFILL_STEP = 8192`, `_QWEN4_WIDE_PREFILL_MIN_TOKENS = 2048+8192`; returned only when model_type startswith `qwen4_exp` AND native QSA AND NAX AND system memory ≥64 GiB. Fed into the paged-cache block-size target so cache ON/OFF share forward boundaries (avoids GDN state boundary mismatch).

**Also load-bearing in the range:**
- **7467dce8 (#3244), 2026-08-29** adds `glm_moe_dsa/csrc/kernels/steel_qwen4_qsa_sparse_gqa.h` (+322, with `MLX_SERVE_LICENSE.txt`). One threadgroup per **(query row, KV head)**; Qwen's **12 query heads per KV head padded to a 16-row Steel MMA tile** (`static_assert(GQA <= H_PAD)`), so both GQA groups reuse each randomly addressed K/V tile **without materializing the gathered K/V tensor**. `kFragSize=8`; fragments Qtile(TQ=1), Ktile(TK=BK/8), Stile, Vtile(1×1), Otile; `static_assert(TQ == 1)`; BK % 8 == 0; threadgroup `Qs[H_PAD*LDQ]`, `KVs[max(BK*LDV, DC*LDK)]`, `selected[BK]`; `padQ/K/V = 16/sizeof(T)`; `kCompressRatio=4`, `kTail=3`; `max_total_threads_per_threadgroup(WM*32)`. **The MMA M axis is the GQA head axis, not the token axis** — one query token per threadgroup, online softmax over block-gathered keys.
- **83a641d2 (#3548), 2026-09-10** adds `qwen35_oq_a8{.cpp,.metal,_nax.metal}` (+583/+164/+418). Routes eligible prompt-processing matmuls through M5 tensor units as **int8 × int8 → int32**, decoding packed Q4/Q5 affine weights **straight into fragment registers**, applying the affine correction at every GS64 boundary; because fragment-slot K assignment is free and the four steps covering one affine group are summed before the correction lands, it "reads the checkpoint's own packed weight stream unmodified". **Measured: Qwen3.8-27B @pp4096, 391.8 → 518.5 tok/s; Q4 GEMM at 42 TOP/s against a measured 44.21 ceiling.** Stage-A `oq_a8_quantize`: one threadgroup per row, `kQuantSimdgroups=8`, each simdgroup owns whole affine groups so residuals `Ra` never straddle a simdgroup and reduce with one `simd_sum`; ACT_MODE 0 = per-row scale, 1 = per-group-of-64 aligned to the weight groups; emits Qa(int8)/Sa(float)/Ra(short). Non-NAX reference kernel keeps it working without tensor units; only `_nax.metal` needs the 26.2 floor.

## 3. mlx-serve (ddalcu/mlx-serve @ 2496d200)

Native **Zig**, no Python (README: "No Python. No cloud. No Electron."). `src/transformer.zig` = **69,102 lines**; drives MLX through mlx-c (`lib/mlx-src`, `lib/mlxc-src`) via `mlx.mlx_fast_metal_kernel*`. **It vendors ds4 as a git submodule**: `.gitmodules` → `lib/ds4` = github.com/antirez/ds4; `src/ds4_ffi.zig` ("1:1 mirror of the public header... Submodule pin: lib/ds4 @ 9139e2a") plus `lib/ds4_metal_sources.zig`. mlx-serve already uses antirez/ds4 as its DSv4-Flash engine.

- **GDN prework**: `gdnPreworkFused` (transformer.zig:36139) returns **six outputs (q,k,v,conv_state,g,beta) from one dispatch**. Args take qkv/b/a at `(off, stride)` per row "so they may all alias one **folded in_proj** output" — qkv, alpha, beta are ONE matmul sliced by offset, not three GEMMs. Requires dk==dv==128. Prefill gate `gdnPrefillFusedFor` (:36100): `seq>=17 && batch<=2 && seq <= hc_prefill.max_seq/batch`, env `MLX_SERVE_GDN_PREFILL_FUSED`; engage log at seq≥512 (:29115). Cold chunk: "Wide prework is token-local; a cold chunk supplies the same zero history as conv1dWithCache" (:29052). Spec-rollback slices the conv INPUT (:29093).
- **Attention**: `msv_attn_p256` fused head-dim-256 flash prefill with an **array-mask arm** for qwen4_exp QSA prefill (gathered K/V), env `MLX_SERVE_QSA_FUSED` (:2698, :2719); a NAX SDPA route (`MLX_SERVE_NAX_SDPA`, :1723/:1737) prefers MLX stock fused SDPA for hd-256 causal prefill and verify blocks >8 rows.
- oMLX README.md:448 confirms lineage: Qwen4 fused GDN decode **and prefill** from `transformer.zig`; QSA's **128-bit K/V staging** from `msv_attn_p256`. transformer.zig:2884-2889 records the loop back: "our own msv_attn_p256 (whose K/V staging their kernel credits in turn)".

**Fundamentally different from a per-layer Metal dispatch loop?** Not the scheduling — mlx-serve is also a per-layer loop. The differences: (1) **no host interpreter**, per-op host cost ns not µs; (2) it *reuses* MLX's steel/fused-SDPA MMA kernels instead of hand-writing every attention variant; (3) **fold-then-slice** — one wide in_proj matmul + offset/stride views instead of separate qkv/alpha/beta GEMMs; (4) **one-dispatch multi-output epilogues**; (5) **128-bit vectorized gather staging** into threadgroup memory feeding simdgroup MMA with the GQA head axis as tile M, so gathered K/V is never materialized. **ds4 already has (5)**: `kernel_qwen4_attn_mm` (metal/qwen4.metal:2404) stages via `device const uint4 *kr`, `kd[u] = kr[u]` for u<4 (4×16 B = 64 B/thread/row), one (kv head, token) per threadgroup, "the query heads of the group as two 8-row tiles, keys in tiles of 16 staged from the selected positions", online softmax, 128 threads (`QWEN4_AMM_KT 16` at :2394), "Same output as kernel_qwen4_attn_decode without key splits, with the queries rounded to half". Only (3) is partly absent in ds4 (separate `lin_alpha`/`lin_beta` GEMVs).

## 4. RECONCILIATION — (a) NOT COMPARABLE, with one genuine residual elsewhere

**Verdict: not comparable.** Every architectural technique #3903 shipped already exists in ds4 in equal or stronger form; the +31.9% is oMLX closing its own Python/host gap against its own pre-PR baseline, and its absolute tok/s are almost certainly warm-resident where our reference points are cold.

1. **Dense/sparse split — already in ds4.** `qwen4_graph_attention_core` (ds4.c:58404) computes `sparse_pos = (g->k_blocks + 1u) * ratio - 1u`, `ratio = 4u`, sends `n_dense = clamp(sparse_pos - cpos0)` rows to the non-gathered arm and the rest through `idx_score`→`idx_select`→`idx_expand`→gathered attention. Same budget-based construction as `token_budget + compress_ratio - 1 - past_len`.
2. **MMA gathered sparse-GQA attention — already in ds4 and already reached at prefill.** `ds4_gpu_qwen4_attn_decode_tensor` dispatches `QWEN4_K_ATTN_MM` when `n_splits == 1 && n_tokens > 8u && head_dim == 256u && n_head/n_head_kv <= 16u`, A/B lever `DS4_QWEN4_NO_ATTN_MM`; `n_splits` is 1 whenever `part` is NULL and `qwen4_graph_attention_core` passes `cT <= 2u ? g->attn_part : NULL`, so prefill chunks take the MMA kernel. In-tree comment: "Keep short prefill tails on the decode arithmetic... **large prefills retain matrix tiles**."
3. **Fused HC residual-write + stream norm — already in ds4.** `kernel_qwen4_hc_combine_norm` (metal/qwen4.metal:4659) is oMLX's new `_WN_SOURCE`; plus `_hc_norm_reuse` (:137) and prefill-specialized `_hc_gate_mix_f16_pf` (:269) / `_hc_gate_mix_pair_f16_pf` (:369); `_hc_combine` (:438) is the tail/mix epilogue.
4. **Fused GDN prework exists and is a superset** — `kernel_qwen4_gdn_front` (:4545) also folds alpha/beta and takes both MTP snapshots. **But it is gated off at prefill**, the one real gap: `qwen4_graph_fused(g,T)` (ds4.c:58283) is true only for T≤2 (T==3 needs `verify_rows_exact`), so at T=8192 ds4 runs 2 extra GEMMs + `conv_stream` + `gdn_prep`. **It cannot be flipped**: the host dispatches `MTLSizeMake(n_k_head, 1, 1)` = **16 threadgroups total** with tokens "walked in order" inside the kernel (:4539-4544). oMLX's grid is `(32, length, 2*hk+hv)`. A ds4 port needs a NEW token-parallel kernel. **Priced ~0.4%, not 30%**: deleting the ga/gb re-reads of `mixed` (2×8192×2560×4 B ≈ 168 MB) and the `gdn_prep` in-place q/k round trip (≈268 MB) saves ≈436 MB per GDN layer ≈ 0.9 ms at ~500 GB/s × 36 layers ≈ 31 ms against a 7.12 s chunk (8192 tok @1150 t/s); dispatch savings ≈2 ms (0.03%).
5. **The baseline is oMLX's own Python engine.** The same release lists three explicitly host-side prefill wins: #3534 "host-side gathering, prefetch, and compiled mean operations" (8-20%), #3469 "host-side decode optimizations", and #3903's own `ShardedEmbedding` PLE rewrite. None exists in a C engine with a precompiled graph. DS4FORK.md:1234 confirms ds4 has no host gap: "65k prefill: 121.9 s GPU-busy vs ~124 s wall → GPU-bound, no host gap."
6. **oMLX's own cold measurements on this exact model contradict the release table.** `/Users/naz/Projects/Scratch/muse-glimmer/flash-next-perf/perf_results2.json` (server-measured, `cached_a: 0, cached_b: 0` = verified cold, non-overlapping nonces) for `Qwen3.8-Flash-Next-oQ4e-mtp`, M5 Max 128 GB: 40k **992 tok/s** (40.6 s), 80k **560 tok/s** (145.3 s), 120k **224 tok/s** (549.4 s). `omlx-ops/README.md:123` explains: "106 GB disk / **69.6 GB resident**", "**requires `qwen4_ple_ssd_offload: true`** on 128 GB (mmaps the 51B hashed n-gram PLE)", "**cold prefill degrades super-linearly** (~1000 tok/s @40k → ~224 @120k, IO-bound)". The release's 1,716 tok/s @64K is **3.1x** the measured cold 560 @80k — same model, hardware, engine family. "Paged caching disabled" ≠ "PLE offload disabled" ≠ "weights warm".
7. **ds4's ~1150 t/s is equally unqualified.** Sole source is an incidental remark, `.codebase-memory/TODO-20260927.md:9` ("agents can regenerate; Qwen3.8 prefill is fast (~1150 t/s)") — **no context length, quant, cold/warm state, or run count**. ds4's *documented* table (DS4FORK.md:1201-1206, DeepSeek-V4 q2-q4 `fixed-0731`, 97.6 GB, chunk 4096): 675-735 @2048 cold, 574-590 @34816, 478-529 @65536, 304 @160k — 2.4x swing from context alone, plus a measured +5-6% cold-start thermal bonus (:1239).
8. **Quant differs and is not neutral.** oQ4e = MLX affine **group-size 64**, 4/5/6/8-bit, fp16/bf16 scales. ds4's Qwen3.8 MoE is gated on `ffn_gate_exps == Q4_K && ffn_up_exps == Q4_K && ffn_down_exps == MXFP4` (ds4.c:58638-58640) — GGUF Q4_K superblocks plus MXFP4 down-projections.
9. **The decode rows are not comparable at all, and ds4 wins them.** 131.5 tok/s is **aggregate over 4 concurrent requests on Qwen3.8-27B** ⇒ ~32.9 tok/s per stream, vs ds4's **47-68 tok/s single-stream** (55 avg @371k) on the larger Flash-Next.

**Where genuine headroom does sit (partially (b), but not via #3903).** PLAN-PREFILL-M5's 0-3% ceiling was derived on DeepSeek-V4 and explicitly put "MoE gemm (roofline)" out of scope (PLAN-PREFILL-M5.md:83-87). That exclusion hides a lever that did not exist when the plan was written (2026-08-31; #3548 landed 2026-09-10): ds4's Qwen3.8 MoE runs **FP16 NAX** (`kernel_qwen4_moe_mm_mid_nax_t<32, half, false>`, metal/qwen4.metal:4199-4202) and ds4 has **no INT8 MMA path anywhere** (verified: no int8/char simdgroup-multiply-accumulate in metal/qwen4.metal or metal/dsv4.metal). oMLX measures **42 TOP/s INT8 vs a 44.21 ceiling** on the same M5 Max, against DS4FORK.md:1268's **~13.5-14 TF/s** float NAX plateau ("the effective M5 tensor-op rate for these tile shapes"). That is ~3x on the bucket DS4FORK prices at **~33% of a 65k chunk (53% at 2k)**.

## 5. Ranked plan for ds4

All candidates: env-gate → balanced A/B with `metal_prefill_variant_bench` → promote only with `--quality` keeping the reference path (PLAN-PREFILL-M5.md:29-35; accumulation order alone changes 129278/129280 logits).

**#1 — INT8-activation MoE prefill GEMM. Expected +10-20% prefill. Risk: high numerics, med-high impl.** Hook: `kernel_qwen4_moe_mm_mid_nax_t` (metal/qwen4.metal:3915) and `_down_nax_t` (:4076), instantiations :4199-4202; host `ds4_gpu_qwen4_moe_mid_grouped_tensor`/`_down_grouped_tensor` from `qwen4_graph_moe` (ds4.c:58636-58669). Add a Stage-A activation quantizer (oMLX `oq_a8_quantize`: one threadgroup per row, 8 simdgroups each owning whole groups so residuals reduce with one `simd_sum`; per-row or per-64 scales + short residuals) and an int8×int8→int32 NAX GEMM applying the affine correction at each group boundary. Gain math: MoE ≈33% of a 65k chunk; 14→42 TOP/s on that bucket ⇒ up to ~22% of total prefill; discount for Stage-A cost and unchanged non-MoE GEMMs ⇒ **10-20%**. Risk: oMLX's "reads the checkpoint's own packed weight stream unmodified" depends on affine GS64 aligning to 4 fragment K-steps — **Q4_K's 8×8 sub-block packing and MXFP4 do not**, so this needs a load-time repack or a Q4_K-specific fragment loader. Exactness: **cannot be bit-exact**; gate `DS4_QWEN4_MOE_INT8=1`, expect `metal_prefill_variant_bench` to fail logit-equality, ship as an opt-in fast path with the FP16 NAX kernel retained as reference. Validate acceptance/quality on real prose before any default flip.

**#2 — Token-parallel GDN prefill front. Expected ~+0.4%. Risk: low-med. Do only alongside #1.** Hook: new kernel beside `kernel_qwen4_gdn_front` (metal/qwen4.metal:4545); host `ds4_gpu_qwen4_gdn_front_tensor` (ds4_metal.m:50250) grid becomes `MTLSizeMake(n_k_head, n_token_blocks, 1)`; gate `qwen4_graph_fused` (ds4.c:58283) gains a prefill arm. Fold `lin_alpha`/`lin_beta` into the `lin_qkv` GEMM (mlx-serve's fold-then-slice) to delete 2 more dispatches. Reuse `conv_blocked` (:618) / `conv_halo` (:607) for the sequential history: conv into scratch with per-block history seeding, then a token-parallel normalize. Exactness: **achievable bit-exact** if the conv window and per-(token,head) L2 reduction order are preserved — the one candidate that can pass `metal_prefill_variant_bench` unchanged. Gate `DS4_QWEN4_GDN_PREFILL_FUSED`; A/B vs `DS4_QWEN4_NO_FUSE=1`.

**#3 — Re-attribute Qwen3.8 prefill before spending on #1. Risk: none. Do this first.** PLAN-PREFILL-M5's attribution is DeepSeek-V4-only, so its 33%/22%/7.5% split is **unverified for Qwen3.8**. Run `DS4_METAL_MOE_STAGE_PROFILE=1` + `DS4_METAL_INDEXER_STAGE_PROFILE=1` + `DS4_QWEN4_TIMING=2` (buckets `ple hc_attn gdn attn hc_ffn moe`, ds4.c:58831-58836) at ctx 16384 and 65536, **cold and warm**, and record the context length this time. Also measure oMLX's claim shape: 16K and 64K, batch 1, median of 3. This is the only way to turn §4's "not comparable" into a number.

**#4 — QSA/indexer tile widening. Expected +2-6% at 65k, more at 160k+. Risk: low.** oMLX moved `query_chunk` 256→1024. ds4's analogue is the indexer score/top-k pipeline. PLAN-PREFILL-M5 Lever 1 (NAX tile retune) was tried **on DSv4**: 81.5→80.3 ms/call ≈0.3%, not promoted; Lever 2 (topk sidecar merge) was negative and reverted. Re-run on Qwen3.8, where the indexer share may differ. Keep the per-(token,comp) accumulation sequence to stay bit-exact.

**No action:** chunk size — ds4's `DS4_QWEN4_PREFILL_CHUNK` default is **already 8192** (ds4.c:39636-39641), exactly oMLX's new `_QWEN4_WIDE_PREFILL_STEP`; `--prefill-chunk` is closed (PLAN-PREFILL-M5.md:85, DS4FORK.md:1227-1228). PLE host gather — ds4 is C, no Python loop to rewrite. ANE — rejected on this model class (`omlx-ops/README.md:376-395`; ANE banks released mid-prefill under memory pressure).

**Separate, non-kernel:** oMLX #3835 partial-block caching cut next-turn prefill 1,174→37 tokens. Check against ds4's KV-cache-v2 lineage work whether prefix reuse can resume at a non-block boundary — `qwen4_session_save_payload` already stores linear layers as FIXED-size `[state][hist]` and attention layers as ROW-scaled slices (TODO-20260927.md payload layout), so the slicing machinery exists. Multi-turn TTFT only.
