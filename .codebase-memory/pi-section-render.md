## 4. Does forceSystemPrompt suppress sections?
**On the wire yes, in the transcript no.** `system-prompt.js:121-125`: a forced prompt yields `{content: forced}` with **no `sections` key**. `agent-session.js:1044-1058` (`_installAgentForcedPromptProjection`) replaces index 0 with `{role:"system", content: forced}` and drops every other system message (`transformed.filter(m => m.role !== "system")`), so persisted section patches never reach the provider while a force is active and `getSystemMessageText` renders only the forced string. Meanwhile `:1021-1023` + `:1031` still diff and persist the structured sections. The force lives solely in `_runSystemPromptOptions` (cleared at `:1100`), so any run that skips `before_agent_start` (`sendCustomMessage({triggerTurn:true})` → `:1504/1507`) loses the projection and the head reverts to the transcript sections — the injected block disappears. That is the reported 378k-token re-prefill.

## 6. Verdict and minimal mitigation
**Improves materially; does not by itself make the head stable.** Gains: (a) the block survives resume and the first request of every custom-message-triggered run (§3) — today that request is guaranteed to re-root (§4); (b) `forceSystemPrompt` stops suppressing `advertised_subagents` and all other sections (§4); (c) `tool_manifest` content is deterministic (sorted names, deduped guidelines, fixed caps — `~/.pi/agent/extensions/tool-manifest.ts:55-93`), so a `prompt()`-to-`prompt()` sequence emits no patch at all. Residual loss: the section inherits exactly the §5 oscillation — one removal patch on the first continuation turn of any non-`prompt()` run, one re-add on the next `prompt()` turn.

**Minimal mitigation, no process-global memo:** put the manifest where `_baseSystemPromptOptions` is built so every turn derives it regardless of entry point. Supported route: `APPEND_SYSTEM.md` (`PI/dist/core/resource-loader.js:824-833`, consumed at `:388` → `system-prompt.js:95-96` `addendum`, wired in by `agent-session.js:1000-1013`) — have `deploy.sh` render `renderToolManifest()` into `~/.pi/agent/APPEND_SYSTEM.md` and drop the `before_agent_start` handler. It is a per-agent-dir file read by each `AgentSession`'s own `ResourceLoader`, not shared mutable state, so it is safe at `globalConcurrencyLimit 3`. Cost: the text becomes deploy-time static (re-run deploy after changing `defaultTools`/guidelines) and `addendum` renders before `project_context`, i.e. near the front — harmless only because it never changes at runtime.

Same shape applies to `advertised_subagents`, which we do not own: the memo-free local bound is to make the catalog constant — leave roster files untouched mid-session, or set `advertise: false` on the file-defined lanes so `buildAdvertisedAgentCatalog` returns `undefined` every turn (`advertised-agent-prompt.js:33-34`) and the section is never created (verify the `subagent` tool description still enumerates the lanes first). The upstream fix is for pi-subagents to pin the catalog into base options too.

**Unverified / residual risks**
- Whether ds4 counts the request `tools` array in the cached prefix. Section patches often ride with `toolsAdded`/`toolsRemoved` (`agent-loop.js:116`, `declareToolChanges`) — an independent re-root source.
- `restoreSystemMessages` (`extensions/runner.js:94-106`) collapses the head into one folded system message whenever a `context` handler changes the conversation; `secret-scrub.ts` is such a handler.
- Dominant real churn is `project_context`: 38 patches across 78 sessions at byte offset 1921 of 40532, so every AGENTS.md edit re-roots nearly the whole head. Fixing `tool_manifest` does not touch it.
- Custom-section order follows handler registration order (`system-prompt.js:106-109`); two extensions setting sections can swap their relative order between processes.
